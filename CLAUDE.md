# CLAUDE.md

Guidance for Claude Code in this repository.

## What this is

**Daftar for macOS**: a native SwiftUI app for an Obsidian vault in a Git repository, meant to replace Obsidian on the Mac. It is the sister of `../notes-droid` (Daftar for Android) and `../notes-linux` (Daftar for Linux, Rust, whose core is a port of `DaftarCore` file by file). The three apps share no code, but they share rules: how a wikilink resolves, what a task line is and how it is ticked, the task statuses and the `[reason:: …]` field, the format of the week notes in `Calendar/`, the config file and the colors. When a rule changes in one, change it in the others. A rule more than one app keeps is written down first in [`docs/specs/`](https://github.com/parham-alvani/notes-linux/tree/main/docs/specs) in `notes-linux`, with the test cases every app must have; a new shared feature starts there, then gets one branch and one pull request per repository, named the same. `web/` is the source of the reader page; `notes-linux/web` is a copy of it.

The repository is **public**; the vault it reads is private. Every test fixture is synthetic.

## Commands: always `just`

```bash
just test   # swift test + node --test for the renderer
just app    # build/Daftar.app, ad-hoc signed
just run    # build and open it
just web    # rebuild the reader bundle only
just icon   # Support/Daftar.icns from art/icon.png
just bench  # the timings of a made-up 20,000-note vault, release build
```

## Layout

```text
Sources/DaftarCore/   no AppKit: parser, link resolver, tasks, calendar, search, git
Sources/DaftarUI/     the SwiftUI app, as a library the tests can drive
Sources/Daftar/       main.swift only
Sources/DaftarQuickLook/ the Quick Look extension (`just app` makes Contents/PlugIns/DaftarQuickLook.appex from it and Support/QuickLook)
Sources/DaftarUI/Reader generated by `just web` from web/src -- never edit, not committed
web/src/              the reading view: markdown-it with Obsidian's syntax
web/dist/quicklook.js generated by `just web` from web/src/quicklook.js, for the Quick Look extension -- not committed
Tests/                swift-testing, synthetic vaults in temporary folders
```

Keep logic in `DaftarCore`: its tests run in a second and need no window. `Tests/DaftarTests` drives the app's own views in-process (the editor's keys, saves and images) on a vault in a temporary folder, with its own `AppSettings(url:)` and `VaultStore(settings:openVault: false)`: a test must never reach the person's config file or vault.

## Toolchain traps

- **No Xcode on this machine, only the command line tools.** In the macOS 27 SDK, `@State` and `@Entry` are macros, and the `SwiftUIMacros` plugin ships only with Xcode. Write `@ViewState` (a type alias of the `State` property wrapper, which no macro shadows) and a plain `FocusedValueKey` or `EnvironmentKey` instead of `@Entry`. Do not build against an older SDK to avoid this: SwiftTerm 1.99 needs the Swift 6.4 standard library of the 27 SDK.
- **The app targets macOS 26** (Liquid Glass, Foundation Models, Writing Tools), so the newest APIs need no `#available`. Without Xcode there is no App Intents metadata processor (Shortcuts and Spotlight actions do not register), no `@Generable` (`FoundationModelsMacros` ships with Xcode), and no Icon Composer: use plain-string Foundation Models calls.
- **Glass does not show in `cacheDisplay`.** The window server draws Liquid Glass, so an off-screen snapshot shows white where glass is. To see it, run the second copy of the app and capture only its window: `screencapture -x -o -l <window number>`.
- **The Quick Look extension is built without Xcode.** It is a SwiftPM executable whose `main.swift` calls Foundation's `NSExtensionMain` (found with `dlsym`), so it needs no `-e _NSExtensionMain` linker flag; `just app` puts it in `Contents/PlugIns/DaftarQuickLook.appex` with `Support/QuickLook/Info.plist`, `quicklook.js` and the reader's CSS. Sign inside out and never with `--deep`: `--deep` signs the extension again without its sandbox entitlement, and Quick Look refuses an extension without the sandbox. Ad-hoc signing is enough on macOS 27.
- **Quick Look shows HTML without running its scripts.** The extension renders the note with the reader's own `render.js` in JavaScriptCore (`QuickLookPreview.Renderer`) and gives Quick Look the finished page; what `reader.js` does to the page afterwards (tag colours, code headers) `quicklook.js` does on the string. Pictures go as `cid:` attachments.
- **macOS takes a Quick Look extension only from an app that was opened once.** `pluginkit -a` or `lsregister` on a build that was never launched gives "plug-ins outside containing apps must be protected by SIP" in `pkd`'s log. To test, copy `build/Daftar.app` with another bundle ID (`me.parham1995.qltest`, extension `me.parham1995.qltest.quicklook`, no URL scheme), sign it again, `open -n` it once, quit it, then `qlmanage -p note.md`; afterwards `pluginkit -r` and `lsregister -u` the copy and delete it, so it never takes `daftar://` or the preview from the installed app. A vault in `/private/tmp` shows no pictures (the sandbox exception covers the home folder only), and one in `~/Documents` makes macOS ask for access to Documents: test in a synthetic folder in the home folder.
- **Core Spotlight refuses an ad-hoc signed app** (`CSIndexErrorDomain -1000`, XPC 4099). `Spotlight` is ready for a signed build and fails silently until then.
- **`Regex` is not `Sendable`.** A shared pattern is `nonisolated(unsafe) static let`; its lazy compile is thread safe, and the index parses notes on many threads.
- **No lookbehind** in Swift regex literals.
- **A test target that depends on an executable target, or on anything with SwiftTerm's build-tool plugin in its graph, loses the swift-testing macro plugin** under the command line tools (`plugin for module 'TestingMacros' not found`). That is why the app is the `DaftarUI` library with a one-line `main.swift`, and why `Package.swift` names `libTestingMacros.dylib` for test targets when Xcode is not installed.
- **A `.task` on a `Group` with nothing in it never runs**: the modifier goes to each child, and there is none. Put a view that waits for its data in a `VStack` (`HeadingLinksBanner`).
- **`Settings` is a SwiftUI scene.** The app's own settings class is `AppSettings`.
- **`UNUserNotificationCenter.current()` aborts outside an app bundle** (`swift run`). `Notifier` checks for a bundle identifier first.
- **A `daftar://` URL opens a new window unless the window says otherwise.** `handlesExternalEvents` on the scene and on `ContentView` keep it in the open window.

## Rules the code keeps

- **A task's statuses are the vault's.** `TaskStatuses` is read from the Tasks plugin's `.obsidian/plugins/obsidian-tasks-plugin/data.json`, and every rule that asks whether a task is open, done or cancelled goes by a status's type, never its character: `[r]` "In Review" is under way exactly as `[/]` is. A `[reason:: …]` field (`TaskReason` in `TaskLine.swift`) is left out of the task's text wherever the text is shown or matched, belongs to the status it was given with, and comes off with any status change unless the change gives a new one. Cancelling asks for the reason. The rules are in `task-reasons-and-statuses.md` of the shared specs.
- **Every setting is in one file, `~/.config/daftar/config.toml`** (`$XDG_CONFIG_HOME` is honoured). Nothing goes into `UserDefaults`. `ConfigFile` reads a small TOML subset and writes a changed value on its own line, keeping the person's comments. A new setting gets a line in `ConfigFile.template`, a property in `AppSettings`, and a control in the Settings window; the app follows edits to the file while it runs. A file that is there and cannot be read (bytes that are not UTF-8) is never written: the app holds the template then, not the person's settings, and says so (`AppSettings.problem`, shown in the Settings window and as the window's notice), as it says a write that failed. The vault's path is written with `~` and not written again while it names the same folder. Window frames that AppKit saves by itself are not settings.
- **What the app keeps for itself is state, not a setting**, and goes in `AppSettings.stateDirectory`: `~/Library/Application Support/Daftar`, or a `state` folder beside the config file in a test or with `$XDG_CONFIG_HOME` set, so a test never writes to the person's Library. What it keeps of each note (`ReadingPlaces`, `PlaceBook`) is such state: the reading place, the folded sections and when the note was last read, in one file for each vault, written a second after a change and on quit. An edit of the app's own marks the note read, so only a pull or another app makes a note "updated since you read".
- **The config folder may be a link.** The dotfiles keep `~/.config/daftar` (`config.toml`, `init.lua`, the home picture) and link the whole folder, not the file: `ConfigFile` is written with `.atomic`, which puts a new file where a link to the file was. Read and watch the folder through the link; never write the config another way than through its folder, and keep state out of it.

- **A file of the vault in a frame runs nothing, and a frame is not heard.** `SchemeHandler.isDocument` says by rule which `vault:` files WebKit would show as a document (HTML, anything with `xml` in its type, a web archive), and each gets `Content-Security-Policy: sandbox`; a list of types missed `application/rss+xml`, whose XHTML `<script>` ran and reached the app. The message handlers answer the main frame only (`Coordinator.hears`).
- **The page names only what the app gave it.** A message from the reader that names a task of another note (`toggleTask`, `editTask`) is taken only for a (path, line) a ` ```tasks ` query of this show answered with, and a `detected` number or address only when `Detected` found it in the note on screen (`PageTrust` in `ReaderView.swift`, made new at each show). The page is drawn from notes; the app never acts on a path or a number only because the page said it.
- **An edit reads the file again and refuses when the line changed.** `VaultEdits.toggleTask` checks that the clicked line is still a task with the status the view showed. Never write from what the view or the index remembers. Before it reads, the store has the editors save (`VaultStore.afterEditors`, `flushEditors`): a tick, a status, the task form, a board drop, Sort Tasks, a tag rename, a restore from the history, a sync and a pull all wait for it, so the edit reads what was typed and no editor writes its older text over the edit. Saving waits for Neovim, so with an editor open such an edit runs a moment later and its `Bool` answer is true; the failure is a notice. A new edit of a note outside an editor goes through the same gate.
- **The index is in memory and is built at launch.** The files are the record; there is no database on disk to migrate. File events are gathered for 250 ms and applied together. The files of `.obsidian` the store keeps a copy of (`FileWatcher.settings`: daily notes, templates, bookmarks, Iconic, `app.json`) are watched too and read again when they change, so a pull's bookmark or daily-notes folder needs no restart. When FSEvents says it lost events (`MustScanSubDirs`, `UserDropped`, `KernelDropped`) the paths it gives are not the files that changed: `VaultStore.rescan` reads the whole vault again, one run at a time.
- **The reader page reaches nothing but two schemes:** `daftar://reader/…` (the bundle) and `vault:///…` (the vault, and nothing outside it). The page has a content security policy; keep `script-src 'self'`, `base-uri 'none'` and `form-action 'none'`. The main frame loads `index.html` when the app asks for it (`Coordinator.loads`) and nothing else, not even another `daftar://reader/` file: a page with no `reader.js` in it would leave the pane dead.
- **A note's raw HTML goes through a list of what is allowed** (`web/src/sanitize.js`, no DOM, so node and Quick Look's JavaScriptCore run it): each tag is read and written again with its listed attributes, so nothing a note writes carries a `class`, an `id`, a `data-*` or an `on*` attribute, which are how the page knows its own controls. `script`, `style`, `iframe`, `svg`, `video` and their like go with what they hold; `meta`, `base`, `link`, `form`, `input` and the rest of HTML go, tag only; a `style` keeps only its listed properties with plain values (no `url(`); a name that is no element (`<first name>`) is shown as text. A new element or attribute for notes is a line in that file's lists and a case in `web/test/sanitize.test.mjs`; what the renderer itself writes (embeds, callouts, tasks) never goes through it.
- **The week notes in `Calendar/` are read-only here.** The phone writes them whole at every change; see `Calendar/CLAUDE.md` in the vault for the format.
- **Git runs with `GIT_TERMINAL_PROMPT=0` and `ssh -o BatchMode=yes`.** A sync that needs a password fails and says so; it never waits. Nor does it wait for a host that is gone: the `ssh` has `ConnectTimeout` and `ServerAliveInterval` (`Git.ssh`, unless the person set `GIT_SSH_COMMAND`), HTTPS has git's low-speed limit, and a command past `Git.limit` (300 seconds) is ended and fails with `timedOut`, so `VaultStore.syncing` cannot stay true for ever. Commit messages use the obsidian-git format of the vault's history: `update notes @ 2026-10-25 09:30:00 on host`. A sync commits nothing on a detached HEAD or a branch with no upstream (`refuseNoBranch`): it says what to do instead. A commit the repository's `pre-commit` or `commit-msg` hook refuses fails with `Git.Failure.hook`, and the notice names the hook and gives its last line.
- **Colors are Daftar's:** naz on dark, Daylight on light, copied from `notes-droid/app/.../ui/theme/Naz.kt` and `Markup.kt`. They are in `web/src/reader.css`, in `Palette` (`WindowModel.swift`) and in the terminal's ANSI palette (`TerminalPane.swift`). Iconic's colour names map to naz as `IconColors.kt` does on the phone.
- **Iconic's icons are Lucide names; the tree draws SF Symbols.** `IconicImage.symbols` maps the ones the vault uses. A new icon in the vault needs a line there; an unknown or missing symbol draws the default icon.
- **The editor is TextKit 2 and never changes text to draw something.** Styling comes from `MarkdownHighlighter` (core, tested); an embedded image gets paragraph spacing and is drawn by `ImageLayoutFragment`, so the text, the cursor and undo see only `![[name.png]]`. An editor save goes through `VaultStore.write`; a change on disk is taken only when nothing is unsaved, as the one range that differs (`take`, never `string =`), and the undo stack goes with it: its steps name places in the old text. A file that does not read as UTF-8 (`VaultStore.isText`) gets no editor and is never written over: read as nothing, it would open empty and the first key would replace it.
- **The editor's code is by part.** `EditorView.swift` is the SwiftUI view and `EditorController`: loading, saving, following the disk, Neovim's start and end. `EditorStyling.swift` styles (an extension of the controller), `NoteTextView.swift` is the text view (carets, panels, margins), `NeovimView.swift` the view in Neovim mode (Neovim's edits, the scroll, the keys to Neovim), `EditorKeys.swift` the plain editor's keys, `EditorContainer.swift` the bar under the text; `EditorCursors.swift`, `EditorModes.swift`, `EditorImages.swift` and `EditorCompletion.swift` are as their names say. A stored property stays in its class's own file; what another file reads is not `private`.
- **The editor styles only what an edit can change.** A key restyles its own lines; the rest of the note is restyled, from the edited line on, only when the note's structure changed -- its fence, `$$`, `%%` and `---` lines, in order (`EditorController.structure`, which runs on every key, so it reads first letters, not every line). A note opens with its first screens styled and the rest a part at a time. Text goes in with `setAttributedString` and plain attributes, never `string =`, which gives it the old text's attributes. A full restyle of a 70,000-character note is about 200 ms; a key must stay under a few.
- **The properties form writes only the lines it changed.** `PropertySheet` (core) keeps each property's lines as written and prints an untouched one byte for byte; a changed one keeps its quotes and its list style. YAML it cannot print back the same (comments, anchors, nested maps, block scalars, a key twice) is never a form: the editor shows it raw. The editor hides the front matter the form shows with attributes (`collapseFrontMatter`) and keeps the cursor and typing out of it (`PropertiesView.swift`); a form edit is `VaultStore.editProperties`, which saves the editors, reads the file again and refuses when the front matter is not the one the form showed. `PropertySheet` has a `RobustnessTests` line.
- **Live preview hides marks with attributes, never by changing text.** Away from the lines the selection is on, `.markup` spans, a markdown link's brackets and address, and a highlight's colour emoji get a 0.01 pt clear font; a quote's `>` and a callout's `[!type]` stay. A selection change restyles the old and the new lines only (`revealSelection`). The cursor never sits in hidden text, so the arrows never stop on it.
- **Many cursors are the editor's own, not the text view's.** `NSTextView` drops a caret from a list of selected ranges and types only into the first range. `EditorExtras.cursors` keeps every cursor, `CaretOverlay` draws the carets the view cannot hold, and the keys reach them through one-line hooks in `doCommand`, `insertText`, `paste` and `mouseDown` (`EditorCursors.swift`); the edits are `MultiCursor` (core, tested). All the edits of one key go in with `shouldChangeText(inRanges:)` in one undo group. The cursors hold while the view's own selection is what they set; a click, a find or an undo ends them. A test has no event loop, so it sets `groupsByEvent = false` to see one undo step for each key.
- **Focus mode dims with a rendering attribute and spelling is the text view's own.** Neither changes the text storage. Spelling forces English for Latin letters (`willCheckTextIn`) and keeps only the marks in `Spelling.parts` (`didCheckTextIn`): not code, links' targets, web addresses, tags, math or the front matter, and not a Persian line while the Mac has no `fa` dictionary (the macOS 27 this was built on has none; the Arabic one marks Persian words wrong).
- **`BufferMirror` keeps each line's UTF-16 length.** A Neovim edit is applied from the changed lines and the one before them, and a position is a sum of lengths: joining or counting the whole buffer at every key made Neovim mode lag in long notes. `BufferMirrorFuzzTests` checks thousands of random edits against a plain copy of the text. The mirror heals itself: the buffer's lines come from Neovim as the first event after the attach (`send_buffer`), in order with the edits, and when an edit does not fit the view's text, or the two are not the same length (`utf16Count`, a sum kept as the lines change), the session takes the whole buffer again.
- **The view scrolls with Neovim's window.** A `WinScrolled` autocommand sends the top line; the view takes it and the cursor together, in one scroll that glides (none with Reduce Motion, none past two screens).
- **The cursor is Neovim's reverse video, never the accent.** `NSPalette.cursor` is the text colour: the caret, Neovim mode's block and bar (`NeovimCursor`), the trail, the particles (`CursorEffectsView`) and the many cursors (`CaretOverlay`) use it. The orange accent looked like the colours of code and markup (an unknown fence, inline code), and a half-clear block over orange text hid both. The block is solid and behind the text, and the letter under it takes the background colour as a rendering attribute (`invertLetter`), so the text, its styles and undo never change; it is set when the block arrives, not on the way. Focus mode's dimming is a rendering attribute too: whoever takes them off the whole note puts the other back (`dim()` calls `showInvertedLetter()`, `invertLetter` calls `dim()`).
- **Neovim mode moves as Neovide does:** `CursorTrail` slides the four corners (the front ones first), `cursor_effect` adds particles to a move in normal mode (never while typing: the bar's slide is enough there, and particles at every key read as a glow around the cursor), and the completion menu and command line blur what is behind them. Each has a setting (`animate_cursor`, `cursor_trail`, `cursor_effect`, `blur_panels`) and none runs with Reduce Motion or Reduce Transparency.
- **` ```tasks ` queries are the phone's engine, ported:** `TasksQuery` and `TaskExpression`. A line they cannot read is listed above the result, never dropped. The page asks the app through the `tasks` message handler, and a note with a query is drawn again when any note changes.
- **Apple Intelligence runs on this Mac only.** `NoteAssistant` uses `SystemLanguageModel.default`, never Private Cloud Compute: the vault holds other people's notes.
- **Escape never takes a Daftar window out of full screen.** An Escape no view used leaves full screen two ways: `NSWindow.cancelOperation(_:)`, and `exitFullScreenMode:`, which SwiftUI's `NSHostingView.doCommand(by:)` calls on the window for a `cancelOperation:` that comes back to it (the reader's `WKWebView` gives back every Escape its page does not take). `SwiftUI.AppKitWindow` has its own `exitFullScreenMode:` that does not call NSWindow's, so `FullScreenEscape` changes both classes, for windows with the `daftar.main` tabbing identifier in full screen. `exitFullScreenMode:` is also View > Exit Full Screen and its key (fn-F on macOS 27), so it is refused only while the current event is the Escape key; every other window keeps AppKit's way.
- **Fonts are settings** (`appearance.font`, `appearance.code_font`), applied by `Fonts` to the editor and the terminal and as CSS variables to the reader. Persian always cascades to Vazirmatn.
- **Neovim mode is the vscode-neovim model:** `nvim --embed` owns the buffer and the file; `NeovimSession` applies each `nvim_buf_lines_event` to the view as the smallest edit (`BufferMirror`) and moves the selection from the cursor autocommand. The view refuses every edit of its own (`shouldChangeText`); text keys go through `interpretKeyEvents` so input methods work, and Control, Command and special keys are sent as Vim notation (`VimKeys`). Neovim saves: `:update` a second after a change and when the note is left -- but never after a delete: `autoread` marks a buffer whose file went away as changed, and the `:update` writes the deleted note back (`stop(writing: false)`). The grid size goes through `VimGrid`: a view off screen has a text container as wide as a CGFloat goes, and `Int(_:)` of that stops the app. Neovim positions are UTF-8 bytes; the view's are UTF-16 -- convert through `BufferMirror`, never by hand. Who owns the text is one answer, `TextOwner` (plain, Neovim starting, Neovim running, Neovim dead), and `saveNow`, `followDisk` and `shouldChangeText` go by it: never ask `session != nil` to decide a save. A Neovim that quit (`:q!`, `:wq`) leaves the view showing the file, so the plain save writes nothing after it; one that was killed leaves its typing in the view, which is saved; one that did not start leaves the plain editor, and is not started again until the note is opened again. Neovim runs with `-n`: a swap file left by a Neovim that died made the next one ask what to do with it, with the keys still waiting for it to start. Nothing waits for Neovim for ever: the start, a save that is waited for and the write at a stop each have a limit (`NeovimSession.startLimit`, `saveLimit`, `stopLimit`), past which Neovim is ended and the text is saved from the view, or from the mirror by the store when the view is another note's. The view shows one buffer, the note's, known by its number: a lines event of another buffer is not the view's text, and a file opened inside Neovim (`:e`, `gf`, a picker) is handed to Daftar to open in the pane (`daftar_open`) while Neovim goes back to the note.
- **Every parser takes made-up text in `RobustnessTests`**, from a fixed seed, so a failure comes back on the next run. A new parser, or a new edit of a whole note, gets a line there: no crash, and the invariant it promises (an edit keeps every line, a sort sorted twice changes nothing, a diff takes the old text to the new).
- **Statuses come from the vault, and a reason belongs to its status.** `TaskStatuses` reads the Tasks plugin's `data.json` (in the index, read again when the file changes; `TaskStatuses.current` is the open vault's, for the rules given only a symbol); a type, not a symbol, says open or closed, and a board column. `TaskReason` reads and writes the `[reason:: …]` field; `ParsedTask.text` is without it. Any change of status (`TaskLine.toggled`, `settingStatus`) drops the old reason unless it gives a new one. The rules are shared with Linux and Android: keep them the same.
- **Sort Tasks is the vault's own `task-sorter` plugin, ported:** done and cancelled tasks first, the open ones last, in each section, by the characters the plugin knows (`[ ]`, `[x]`, `[X]`, `[-]`). A task takes the lines indented under it, by any number of spaces, and nothing in a code fence is a task or a heading. Keep `TaskSorter` and the phone's port the same.
- **A sync never commits over an open rebase.** A pull that stops on a conflict throws `Git.Stopped` and leaves the rebase open (`rebase-merge` or `rebase-apply`); `VaultStore.rebasing` then stops every sync until the person finishes or aborts in `ConflictSheet`. Before this, the next sync committed the conflict marks on a detached HEAD and every later pull failed. In a rebase git's "ours" is the upstream and "theirs" is the person's commit: say "On the remote" and "Your change", never ours and theirs. `rebase --continue` runs with `GIT_EDITOR=true`, in a loop, since the next replayed commit can stop too, and after `git add -A`: it refuses a tree with changes that are not staged, and the person may tick a task or capture a line while the conflict waits, which then goes into the replayed commit. A pull over changes not yet committed (Pull, the pull at launch) keeps them aside with `--autostash`, and git exits 0 when they do not fit back: the files have conflict marks and no rebase is open. `Git.pullRebase` looks for unmerged files after every pull and throws `Stopped(unstashed: true)`; the same sheet resolves them (`VaultStore.unstashing`, `Git.finishUnstash`: the upstream is "ours" there too), the changes end up unstaged as they were, the pull's `autostash` entry is dropped, and there is no Abort, since the pull is done. Pull still commits nothing: a commit first would make a pull depend on the vault's pre-commit hook. An abort resets the tree, so `Git.abortRebase` reads what the person wrote in other files while the rebase was open (edited, added, deleted) and writes it back after `rebase --abort`; only the conflicted files' choices are lost. `ConflictText` parses and resolves the marks and has a `RobustnessTests` line.
- **A note's history is `git log --follow`** (`Git.history`), and a restore is an ordinary `VaultStore.write`: the next sync commits it, so nothing in the history is lost.
- **The Quick Look preview reads, it never writes**, and follows no link. Its sandbox lets it read the home folder (`temporary-exception.files.home-relative-path.read-only`) for the pictures a note embeds; it scans the vault (the folder above with `.obsidian`) only when the note has links, and only the note's own folder when it is in no vault. It asks no site for anything: `quicklook.js` always renders with pictures from the web off (a placeholder, which nothing there can click), the page carries `QuickLookPreview.policy` (its `cid:` attachments, `data:` pictures and inline styles only), and `attach` resolves symlinks as `VaultStore.file` does, so a link in the vault to a file outside it is not attached.
- **A canvas is read-only and drawn by the reader.** `Canvas` (core) decodes JSON Canvas leniently: an unknown key or node type, a missing id or an edge to nowhere is dropped, never an error. `web/src/canvas.js` draws the board; a file card's note is filled as an `![[embed]]`, and a checkbox on the board is never ticked. Preset colours `1`-`6` map to the palette's red, orange, yellow, spring green, aqua and purple.
- **A picture is read, never edited.** `Vault.isImage` (core) is the list of types WebKit draws; such a file opens in the pane on the reader's picture page (`showImage` in `web/src/reader.js`), loaded from `vault:` with its date in the address so a changed file loads again. `NotePane.canEdit` is false for it, so the editor never opens a binary file; the commands that read a note's text check `WindowModel.showsText`, and the palette drops `PaletteCommands.textOnly`. Zoom and pan are `PanZoom` (`web/src/viewer.js`, its math tested in node), for the picture page and for a picture opened large from a note: the picture is laid out at its natural size times the zoom (width and height, not a transform's scale), so an SVG or a diagram is drawn again at each size and stays sharp. The editor draws an animated picture's frames with `ImageAnimation` and `ImageAnimator` (`EditorImages.swift`), which only redraw the lines on screen.
- **A web view in a window behind others does not paint.** To capture the app's page with `screencapture -l`, bring the test copy to the front first (`NSRunningApplication(processIdentifier:).activate()`); a hidden window shows an empty reader that is not a bug.
- **Replace in Vault writes only what the preview showed.** `VaultReplace.replace` runs the match again on the text read from disk and refuses the note when its matches are not the ones shown; the write is `VaultStore.write`. Find and replace share `VaultReplace.Pattern` (an `NSRegularExpression`, so lookbehind works there), and "Skip code" uses `TagRename.fence`.
- **Sections and heading links follow the outline.** `Sections` (core) finds headings as `NoteParser` does (no setext headings, none in front matter, fences or comments; `RobustnessTests` checks they agree; inline code is read first, by `InlineCode` in `NoteParser.swift`, so a `%%` in a code span opens no comment and a link in code or in `$…$` math is no link), and a section runs to the next heading of its level or above. A section moved keeps the blank lines after each section in place. `HeadingRename` finds a link's heading as Obsidian does (`HeadingRename.key`: no marks, no case; each `#` part under the one before; the first match wins). The editor compares its headings when the cursor leaves a heading line or the editor, never at a key; the links are written with `HeadingRename.apply`, which refuses a line that is not the one the preview showed, through `VaultStore.write`.
- **The reader and the editor have one measure.** `appearance.text_width` em (0 the whole window) is `--text-width` on `#note` and `NoteTextView.sideMargin` in the editor; under 720 points a pane's margins are 16 points in both (`narrowPane` and the `@media (max-width: 719.98px)` rule). Change one, change the other.
- **Export as PDF runs `daftar-cli export`** (`PDFExport.swift`; the spec is `docs/specs/export.md` in notes-linux), so the app, a script and Daftar for Linux make the same PDF: the `daftar-cli` beside the app's binary, else on `$PATH`, else Homebrew's or Cargo's (an app opened from the Finder has no Homebrew on its `$PATH`). The editors save first, as the command reads the file; the command's last line of stderr is the notice when it fails. `export.logo` and `export.footer` are the command's settings, in the template for it; the app reads neither.
- **`daftar-cli` runs through `DaftarCLI`, and only through it** (`DaftarCLI.swift`): Export as PDF, the Problems panel, format on save, search by meaning and its index, and the weekly review. It is found as Export as PDF finds it, run off the main thread in the vault's folder (a note's path is read from there too), both pipes read as they fill, each stderr line given to a callback when asked (an index build's progress), stdin written with `F_SETNOSIGPIPE`, at the priority the feature asks (`.utility` for an audit, `.background` for a refresh of the index), and ended when its task is cancelled (SIGTERM, SIGKILL a second later). Every command running is in `DaftarCLI`'s registry, and `AppDelegate.applicationWillTerminate` ends them all (`endAll`), so no `semantic-index` build or audit outlives the app. A `daftar-cli` that refuses a flag the app needs says so once in the feature's own words ("Problems and Format Note need daftar-cli 0.23.0 or later", "Search by meaning needs…"), never as an error of the vault.
- **The Problems panel is `just audit` and `just check` inside the app** (`VaultChecks.swift`, `ProblemsView.swift`; findings parsed in core by `Problems`): `check --json` (with `--profile audit` when `.daftar.toml` has an `[audit]` section), `lint --json` and `fmt --check --json`, one after another at `.utility`, when the vault opens (only a vault with `.daftar.toml`, `.markdownlint.jsonc` or `.prettierrc`; any other when the panel opens) and two seconds after files change. One audit at a time: a change while one runs asks for one more after it. A fix is `just fix`'s command (`lint --fix`, `check --fix`, `fmt`) on the note or the vault, after `flushEditors`, and the note is read again after; no fix writes from what the panel remembers. The editor's margin dots (`EditorProblems.swift`) are drawn in `drawBackground` and never change the text.
- **Format on save formats on leaving, never at the autosave** (`NoteFormat.formats`, core, tested): another note, the editor's view going (⌘E, a closed pane or window), Quit; and only a note whose file is not what the editor took (`loadedText`), so reading a note in the editor changes nothing. The file is formatted after the editor saved it (a Neovim that was let go is awaited through `EditorController.stopping`), with `fmt --stdin`, and written only when the file is still the text that was formatted. Format Note in the plain editor replaces the one range that differs as one undo group; in Neovim mode it sets the changed lines with `nvim_buf_set_lines` (one step of Neovim's undo) and writes. No `daftar-cli`, or one too old, formats nothing and says nothing, except on the command.
- **Search by meaning is `daftar-cli`'s** (`MeaningSearch.swift`; `Meaning` in core reads its JSON and its failures; the spec is `docs/specs/meaning-search.md` in notes-linux): `search --meaning-only --json`, `related --json` and `semantic-index`, run by `DaftarCLI` in the vault's folder. A search waits for a pause in the typing and cancels the run before it. Exit 3 is a model not downloaded, and the one row offers the download; a usage error about these flags is an old `daftar-cli`, said once and not asked again until the binary changes. The model is never downloaded unasked, and the background refresh (`meaning.refresh_minutes` after the last change, `.background` priority, one build at a time) runs only once the model is there.
- **The dark palette is screen-only** (`@media screen and (prefers-color-scheme: dark)` in `reader.css`), so a PDF export or a print is always in Daylight.
- **The reading cursor is a block with a band on one line of it.** `reading` in `web/src/reader.js`: a block is the innermost element with a `data-line`; its lines are the rects of its text nodes (not a nested list, a picture or KaTeX's hidden text) merged where they share most of their height (`rows`). `j`/`k` go a line at a time and on to the next block after its last line; a block of one line has no band. The file line of a line (`sourceLine`) is the block's line plus the `\n` in its text before the line's start, found with `caretRangeFromPoint` (soft breaks stay `\n` since markdown-it runs with `breaks: false`; a fence adds one); off screen it is unknown, never guessed. `appearance.reading_line` is the band's strength, 0 none. After a scroll, a cursor left off screen comes to the first line on screen (`follow`), so `NotePane.cursorLine` is always where the person reads: ⌘E opens the editor there and the reader comes back to the editor's line. That hand-off is the pane's, both ways; test it end to end.
- **The reader stays loaded under the editor.** `NotePane`'s content is a `ZStack`: the editor over a hidden `ReaderView` with `active: false`, which draws nothing new and takes no keys (`Coordinator.paused`), and whose `onCursor` and `onSection` are ignored while the pane edits. Back to reading, the page saves the editors first (`flushEditors`, so it draws what Neovim just wrote), draws at the editor's line and calls `onShown`; until then the editor stays over it (`NotePane.readerShown`, with a 0.5 s fallback), so the page is never seen blank or at its old place. Into the editor, `go(toLine:)` centres the view on the line before Neovim runs, and `NeovimSession.start` puts Neovim's cursor there before its cursor reports begin, so the cursor never slides from line 1. A Neovim cursor whose place in the text did not change (`neovimCursorAt`) moves at once: a relayout or a scroll is not a move.
- **New Task (⌥⌘T, File menu and palette) is the task form with a note and a section.** `WindowModel.newTask` fills in the note on screen and the heading the cursor is under (the scratchpad with no note); `TaskLine.written` makes the line, with today as its ➕ created date, and `VaultStore.addTask` puts it at the end of that heading's section with `QuickCapture.append(_:to:headingLine:)`, through the editors' gate, reading the file again. The heading is found by its line, not its name, so two `## Work` sections are two places. The form's Created row edits ➕ on any task.
- **Drill is `daftar-core`'s `drill.rs`, ported, and shares its state file.** `Drill` (core) makes the same cards, ids (`path#Heading#Under it`) and SM-2 schedule, and `DrillState` reads and writes `$XDG_STATE_HOME/daftar/drill-<FNV-1a of the vault's path>.json` (else `~/.local/state`) byte for byte as serde_json does (`DrillTests` has a file the CLI wrote), never `stateDirectory`: the app, `daftar-cli drill` and the MCP `drill_*` tools share one history. A test's `AppSettings` keep it in their own state folder (`AppSettings.drillFolder`). A rating reads the file again and writes through a temporary file and a rename, so a rating made elsewhere is kept. `DrillDeck` (on the store) reads the deck off the main thread; the answer is the reader given the section's text (`ReaderRequest.text`), which ticks no task, keeps no folds and takes no keys, since its lines are not the file's; it lays out hidden (`isHidden`, so VoiceOver does not read it early) and only paints on the flip. The page's keys are a local monitor by key code, so they work in any keyboard layout.
- **An error in `daftar.show` leaves the page at its top, silently.** The note is drawn, then the scroll, folds and reading cursor are skipped. A reference to a name that is not there (`scrollToLine` once used an `anchor` it was never given) did this for every return from the editor. The node tests do not load `reader.js`; a change to it gets a test in a real `WKWebView` (`ReadingCursorTests`, `ImagePageTests`), which also catches a page that never gets ready.
- **A `@MainActor` suite's `.enabled(if:)` deadlocks the whole test run before it starts.** Put the condition in a global constant.
- **A window has one or two note panes (`NotePane`).** Each pane has its own note, mode, history and find; `WindowModel` keeps the panes and the focused one, and its `request`, `editing`, `path` and history commands act on the focused pane, so menus, quick open and the inspector follow the focus. A click in a pane gives it the focus (`PaneClicks`, a local mouse monitor) before the click acts. The editor saves when it stops being first responder and takes the file when it becomes first responder again with nothing unsaved, so the same note in the editor of two panes does not lose text. In Neovim mode only one pane edits (`WindowModel.oneEditor`): two Neovims would each own the same file. The split is not kept across launches; no window state is.
- **The Dock badge, the alerts and Spotlight follow the vault for the app, not for a window.** `VaultFollower` (`DaftarApp.swift`) hears the store's changes with `withObservationTracking`, started from the menu bar icon's label as quick capture is, so each change is followed once however many windows are open, and with none open. Never hang such work on a window's view. `Spotlight` stops after the index refuses a batch (an ad-hoc build always does), until the next launch.
- **Quick capture works with no window open.** The store belongs to the app; `QuickCaptureController` gets it from the menu bar icon's label, which is there from launch. The shortcut is a Carbon hot key (`RegisterEventHotKey`, no Accessibility permission) and the panel is a non-activating `NSPanel`, so the app in front stays in front. A capture saves the editors, reads the file again and writes with `VaultStore.write`; `QuickCapture.append` (core) keeps every line. `capture.heading` is filled as a template is (`VaultStore.captureHeading`), so `## {{date:YYYY-MM-DD}}` gives one inbox note a section for each day.
- **Services (Add to Daftar Scratchpad, New Daftar Task) work with no window.** `NSServices` in `Support/Info.plist` and `DaftarServices` (`Services.swift`), the app's `servicesProvider` from launch, with the store quick capture has, waited for while it loads. The scratchpad line is written by `VaultStore.addToScratchpad` (the editors' gate, the file read again, `QuickCapture.append` under `## <today>`), and a failure opens quick capture with the line, so nothing sent is lost. New Daftar Task sends `daftar://new-task?text=` to this process as an Apple event (`openInThisApp`), so SwiftUI makes a window when none is open and the installed app never gets a test build's address; the address only fills the form. To try a service from a test build, give a copy its own bundle ID, name and `NSPortName`, start it with `open -n` and a test `XDG_CONFIG_HOME` first (a service that has to launch the app gives it no environment, so it would read the real config), then `lsregister -f` it and `/System/Library/CoreServices/pbs -update`.
- **The scratchpad is one note.** ⌥⌘S (File › Scratchpad, the palette) opens `scratchpad.note`, a vault path, `Scratchpad.md` when not set: made empty when it is not there, opened in the editor with the cursor at its end, and nothing is written into it by opening it. It never makes a note for each day or a folder; the older `scratchpad.folder` key is not read and not rewritten. The vault keeps one inbox with dated sections, as Daftar for Android's `scratchpadPath` does; quick capture reaches the same note with `capture.target` and a dated `capture.heading`. Daftar for Linux has to follow.
- **Every control has a name VoiceOver can say.** An icon-only button gets `.accessibilityLabel` (and `.help`); a decorative image is `.accessibilityHidden(true)`; a row drawn with `onTapGesture` gets `accessibilityRow` (`Accessibility.swift`); what a colour or an icon alone says (status, priority, overdue, a dot, the focused pane) is said in words, from `Spoken` (core) for tasks. In the reader every control is a real `<button>` or has a `role` and a name (`web/src/controls.js`, tested in `web/test/a11y.test.mjs`). Animations go through `withMotion` or `motionAnimation`, and faint text through `.faint()`, so Reduce Motion and Increase Contrast hold. `AccessibilityTests` reads the views' tree with `NSAccessibility`; SwiftUI builds that tree only after the app gets `AXEnhancedUserInterface`, which the test sets.
- **The home page decodes its picture once.** A pane with no note shows `HomeView`; `HomePictures` decodes `home.image` off the main thread with ImageIO (no larger than 5120 px, as EXIF turns it) and keeps it by path and modification date, so a redraw never decodes. The page reads Beautitab's `data.json` (`Beautitab`, core, lenient) again each time it appears, never goes to the network (a web address or an online quote source is off), and the picture is `.accessibilityHidden`. ImageIO reads WebP but cannot write it: a test's WebP is a byte literal.
- **Hidden files leave the lists, never the index.** `ExcludedFiles` is Obsidian's `userIgnoreFilters` and the `files.hidden` names (whole file names, in any folder); `VaultStore.excluded` is what the lists leave out now (nothing while `files.show_hidden` is on), `VaultStore.hidden` the rule itself, which Spotlight follows. A list a person browses (the tree through `store.tree` and `store.folder`, quick open, search, the graph, backlinks, recent notes, Today, the board) filters with `store.excluded`; the resolver, the reader and `daftar://open` never do, so a link or an embed to a hidden file still works.
- **A block id is read the same in the app and the reader.** `BlockRefs` (core) and `blockIds` in `web/src/render.js`: a trailing ` ^id` names its paragraph or list item (the `<li>`, since a tight list draws no `<p>`), and a `^id` line of its own, after an empty line, names the table, quote or code block above it. A new id is six lowercase letters and digits, free in the note, and goes in through the editor (a step to undo) or `VaultStore.addBlockId`, which reads the file again and refuses a block that changed. The editor's completion list shows labels (`alias → Note`, an indented heading, `#tag  3`); `CompletionState.choices` maps each label to the text it writes, so a label never goes into the note.
- **The job search is `job_search.rs` ported.** `JobSearch` (core) reads applications from the index's front matter (`job_stage` and the other `job_` keys), its stages, channels, `upcoming` and `forMeeting` follow the Rust tests, and `QuietRules` is `memory.rs`'s `memory-quiet` (`.daftar.toml`'s `active` and `quiet_days`). `job_next` is a wall-clock time in Europe/Madrid (`LocalTime.zone`), whatever the Mac's zone. The board (`JobBoardView`) reads it off the main thread at each index revision; a drop is `VaultStore.setJobStage`, through the editors' gate, which writes the one `job_stage` line with `PropertySheet` and refuses when the note's stage is not the card's. It writes nothing else: not `Tasks/Interviews.md`, not the history.
- **Holidays are code, not vault data.** `CalendarEvents` (core) is the table of `calendar_events.rs` in notes-linux and `docs/specs/calendar-events.md`; a change to a day changes all three apps. An event's note is the vault's note named by its title (`VaultStore.note(of:)`), never made by the app. `DayPicker` draws a `Month` (core): Gregorian from Monday, or with `appearance.persian_calendar` the Jalali month from Saturday, read from the right; a day picked is always written as its Gregorian `YYYY-MM-DD`.
- **`appearance.remote_images = false` asks no site for a picture, by two rules.** The renderer: every picture a note or a base draws is written by `picture` in `web/src/render.js` (`![…](…)`, a raw `<img>`, a base card's cover), which reads the address as the browser does (`pictureAddress`: `https:/x`, `https:x`, a tab or a character reference in the scheme are all `https://x`; an `http:` picture is asked for over https) and writes a `remote-image` placeholder; there is no HTML to search afterwards. The page's policy: `SchemeHandler` serves `index.html` with `img-src` without `https:` while the setting is off (`noRemotePictures`), so what the renderer misses (Mermaid asks for a picture shape itself) is refused before any site is asked; a change of the setting loads the page again. A click on a placeholder asks the app (`remoteImage` handler), which allows that one `https:` address for the note on screen and answers with a `daftar-remote:` address that `RemotePictures` serves; an address nobody clicked is refused there. The host only sends `remoteImages` with `daftar.show` (`ReaderView.appearance`). The spec is `docs/specs/remote-images.md` in notes-linux.
- **The terminal is SwiftTerm, pinned exactly.** It runs the login shell in the vault's folder and lives in the window's model, so hiding the pane keeps the shell.

## Performance

`just bench` (`BenchmarkTests`, on only with `DAFTAR_BENCH=1`) writes a vault from a fixed seed: 20,000 notes in nested folders, 53,000 tasks, front matter, links (broken, with an alias, with a heading), ` ```tasks ` queries, 70,000-character notes, Persian text, images and bases. It prints a table of the paths a person waits on. The budget on an M4 Pro, with the release build:

| Path | Budget |
|---|---|
| Open the vault (index and full-text search) | under 2.5 s |
| A saved note (watcher batch of 1) | under 150 ms |
| A pull of 500 changed files | under 300 ms |
| Full-text search | under 50 ms |
| Quick open, each key | under 100 ms |
| A ` ```tasks ` query over every task, or the Today page | under 100 ms |
| The whole-vault graph and its layout | under 1.5 s |
| Rename a note that 2,000 notes link to | under 1.5 s |
| Rename a tag in 6,000 notes | under 2 s |

A change that makes a row slower than its budget is a bug. To find a slow path, run it in a loop and `sample <pid>` the test process (Instruments needs Xcode). Rules the timings taught:

- **A regular expression runs only on a line that has its marks.** Swift's `Regex` is slow: test for the ASCII marks it needs first (`hasMark("[[")`, `mayHoldTag`), on the UTF-8 bytes, not with Foundation's `contains`. The test must be a condition the pattern cannot match without, so the result never changes.
- **No regex literal and no `Calendar(identifier:)` inside a function that runs per line or per task;** make it a `static let`.
- **A sort compares values worked out before it**, not in its comparator: titles, query groups, and positions rather than large structs.
- **`derive()` makes the resolver and the tree again only when the files changed.** A saved note changes neither.
- **The search table deletes by rowid.** Its `path` column is not indexed; a delete by path reads the whole table.
- **Work on many independent files or nodes is shared out with `concurrentPerform`**, each in its own slot of an `UnsafeMutableBufferPointer`, with the same order of operations, so the result is the same to the last bit. Deinitialize the buffer before it is deallocated, or what it holds leaks.

## Testing the app

The installed app comes from Homebrew only (`brew install --cask parham-alvani/tap/daftar`): a release (`VERSION` and a `v*` tag) reaches the tap's cask, and the cask installs it. A release is `VERSION` bumped in its own commit and a `v*` tag; CI takes about twenty minutes, then the tap's `bump` workflow (`gh workflow run bump.yaml` in `homebrew-tap`) moves the cask, and `brew upgrade --cask parham-alvani/tap/daftar` installs it. A running Daftar keeps its old code until it is quit and opened again: check its start time against the release before calling a fix missing. Never copy a test build into `/Applications`; that makes the cask install fail and hides which version is installed. Test from `build/Daftar.app` (`just app`), with `open -n` and a test `XDG_CONFIG_HOME`; a build run from `build/` asks for notification permission again. The vault is the `vault` line of the config file. `open "daftar://open?path=Folder/Note.md"` opens a note, `daftar://open?path=today` the Today page, and `daftar://terminal` the terminal. A debug build makes the web view inspectable in Safari.

A Carbon hot key fires for a synthetic key only when the modifier keys go down first, as on a keyboard (`CGEvent` at `.cghidEventTap`); a key posted to the app's pid never reaches it.

**Do not click a task in the real vault to test.** A tick writes the file, and with automatic sync on, it commits and pushes. Test writes on a copy, or with the unit tests.
