# CLAUDE.md

Guidance for Claude Code in this repository.

## What this is

**Daftar for macOS**: a native SwiftUI app for an Obsidian vault in a Git repository, meant to replace Obsidian on the Mac. It is the sister of `../notes-droid` (Daftar for Android) and `../notes-linux` (Daftar for Linux, Rust, whose core is a port of `DaftarCore` file by file). The three apps share no code, but they share rules: how a wikilink resolves, what a task line is and how it is ticked, the task statuses and the `[reason:: …]` field, the format of the week notes in `Calendar/`, the config file and the colors. When a rule changes in one, change it in the others. A rule more than one app keeps is written down first in [`docs/specs/`](https://github.com/parham-alvani/notes-linux/tree/main/docs/specs) in `notes-linux`, with the test cases every app must have; a new shared feature starts there, then gets one branch and one pull request per repository, named the same. `web/` is the source of the reader page; `notes-linux/web` is a copy of it. A lesson that holds for any desktop app (a trap of SwiftUI, AppKit or TextKit, a data-safety rule, a way to measure) also goes into the `taller` plugin for Claude Code, which gathers the three apps' lessons, with its reason and commit; this file keeps what is about this app.

The repository is **public**; the vault it reads is private. Every test fixture is synthetic.

## Commands: always `just`

```bash
just test   # swift test + node --test for the renderer
just app    # build/Daftar.app, ad-hoc signed
just run    # build and open it
just web    # rebuild the reader bundle only
just icon   # Support/Daftar.icns from art/icon.png
just bench  # the timings of a made-up 20,000-note vault, release build
just bench-editor  # the plain editor's main thread per key and frame, on a long note
```

## Layout

```text
Sources/DaftarCore/   no AppKit: parser, link resolver, tasks, calendar, search, git
Sources/DaftarUI/     the SwiftUI app, as a library the tests can drive
Sources/Daftar/       main.swift only
Sources/DaftarQuickLook/ the Quick Look extension (`just app` makes Contents/PlugIns/DaftarQuickLook.appex from it and Support/QuickLook)
Sources/DaftarUI/Reader generated by `just web` from web/src -- never edit, not committed
web/src/              the reading view: markdown-it with Obsidian's syntax
web/dist/quicklook.js generated by `just web` from web/src/quicklook.js, for the Quick Look extension -- not committed
Tests/                swift-testing, synthetic vaults in temporary folders
```

Keep logic in `DaftarCore`: its tests run in a second and need no window. `Tests/DaftarTests` drives the app's own views in-process (the editor's keys, saves and images) on a vault in a temporary folder, with its own `AppSettings(url:)` and `VaultStore(settings:openVault: false)`: a test must never reach the person's config file or vault.

## Toolchain traps

- **No Xcode on this machine, only the command line tools.** In the macOS 27 SDK, `@State` and `@Entry` are macros, and the `SwiftUIMacros` plugin ships only with Xcode. Write `@ViewState` (a type alias of the `State` property wrapper, which no macro shadows) and a plain `FocusedValueKey` or `EnvironmentKey` instead of `@Entry`. Do not build against an older SDK to avoid this: SwiftTerm 1.99 needs the Swift 6.4 standard library of the 27 SDK.
- **The app targets macOS 26** (Liquid Glass, Foundation Models, Writing Tools), so the newest APIs need no `#available`. Without Xcode there is no App Intents metadata processor (Shortcuts and Spotlight actions do not register), no `@Generable` (`FoundationModelsMacros` ships with Xcode), and no Icon Composer: use plain-string Foundation Models calls.
- **Glass does not show in `cacheDisplay`.** The window server draws Liquid Glass, so an off-screen snapshot shows white where glass is. To see it, run the second copy of the app and capture only its window: `screencapture -x -o -l <window number>`.
- **The Quick Look extension is built without Xcode.** It is a SwiftPM executable whose `main.swift` calls Foundation's `NSExtensionMain` (found with `dlsym`), so it needs no `-e _NSExtensionMain` linker flag; `just app` puts it in `Contents/PlugIns/DaftarQuickLook.appex` with `Support/QuickLook/Info.plist`, `quicklook.js` and the reader's CSS. Sign inside out and never with `--deep`: `--deep` signs the extension again without its sandbox entitlement, and Quick Look refuses an extension without the sandbox. Ad-hoc signing is enough on macOS 27.
- **Quick Look shows HTML without running its scripts.** The extension renders the note with the reader's own `render.js` in JavaScriptCore (`QuickLookPreview.Renderer`) and gives Quick Look the finished page; what `reader.js` does to the page afterwards (tag colours, code headers) `quicklook.js` does on the string. Pictures go as `cid:` attachments.
- **macOS takes a Quick Look extension only from an app that was opened once.** `pluginkit -a` or `lsregister` on a build that was never launched gives "plug-ins outside containing apps must be protected by SIP" in `pkd`'s log. To test, copy `build/Daftar.app` with another bundle ID (`me.parham1995.qltest`, extension `me.parham1995.qltest.quicklook`, no URL scheme), sign it again, `open -n` it once, quit it, then `qlmanage -p note.md`; afterwards `pluginkit -r` and `lsregister -u` the copy and delete it, so it never takes `daftar://` or the preview from the installed app. A vault in `/private/tmp` shows no pictures (the sandbox exception covers the home folder only), and one in `~/Documents` makes macOS ask for access to Documents: test in a synthetic folder in the home folder.
- **Core Spotlight refuses an ad-hoc signed app** (`CSIndexErrorDomain -1000`, XPC 4099). `Spotlight` is ready for a signed build and fails silently until then.
- **`Regex` is not `Sendable`.** A shared pattern is `nonisolated(unsafe) static let`; its lazy compile is thread safe, and the index parses notes on many threads.
- **No lookbehind** in Swift regex literals.
- **A test target that depends on an executable target, or on anything with SwiftTerm's build-tool plugin in its graph, loses the swift-testing macro plugin** under the command line tools (`plugin for module 'TestingMacros' not found`). That is why the app is the `DaftarUI` library with a one-line `main.swift`, and why `Package.swift` names `libTestingMacros.dylib` for test targets when Xcode is not installed.
- **A `.task` on a `Group` with nothing in it never runs**: the modifier goes to each child, and there is none. Put a view that waits for its data in a `VStack` (`HeadingLinksBanner`).
- **`Settings` is a SwiftUI scene.** The app's own settings class is `AppSettings`.
- **`UNUserNotificationCenter.current()` aborts outside an app bundle** (`swift run`). `Notifier` checks for a bundle identifier first.
- **A `daftar://` URL opens a new window unless the window says otherwise.** `handlesExternalEvents` on the scene and on `ContentView` keep it in the open window.

## Rules the code keeps

- **A task's statuses are the vault's.** `TaskStatuses` is read from the Tasks plugin's `.obsidian/plugins/obsidian-tasks-plugin/data.json`, and every rule that asks whether a task is open, done or cancelled goes by a status's type, never its character: `[r]` "In Review" is under way exactly as `[/]` is. A `[reason:: …]` field (`TaskReason` in `TaskLine.swift`) is left out of the task's text wherever the text is shown or matched, belongs to the status it was given with, and comes off with any status change unless the change gives a new one. Cancelling asks for the reason. The rules are in `task-reasons-and-statuses.md` of the shared specs.
- **Every setting is in one file, `~/.config/daftar/config.toml`** (`$XDG_CONFIG_HOME` is honoured). Nothing goes into `UserDefaults`. `ConfigFile` reads a small TOML subset and writes a changed value on its own line, keeping the person's comments. A new setting gets a line in `ConfigFile.template`, a property in `AppSettings`, and a control in the Settings window (and, when a vault may set it, a line in `ResolvedSettings.allowed` and the shared spec's table); the app follows edits to the file while it runs. A file that is there and cannot be read (bytes that are not UTF-8) is never written: the app holds the template then, not the person's settings, and says so (`AppSettings.problem`, shown in the Settings window and as the window's notice), as it says a write that failed. The vault's path is written with `~` and not written again while it names the same folder. Window frames that AppKit saves by itself are not settings.
- **What the app keeps for itself is state, not a setting**, and goes in `AppSettings.stateDirectory`: `~/Library/Application Support/Daftar`, or a `state` folder beside the config file in a test or with `$XDG_CONFIG_HOME` set, so a test never writes to the person's Library. What it keeps of each note (`ReadingPlaces`, `PlaceBook`) is such state: the reading place, the folded sections and when the note was last read, in one file for each vault, written a second after a change and on quit. An edit of the app's own marks the note read, so only a pull or another app makes a note "updated since you read".
- **The config folder may be a link.** The dotfiles keep `~/.config/daftar` (`config.toml`, `init.lua`, the home picture) and link the whole folder, not the file: `ConfigFile` is written with `.atomic`, which puts a new file where a link to the file was. Read and watch the folder through the link; never write the config another way than through its folder, and keep state out of it.

- **A file of the vault in a frame runs nothing, and a frame is not heard.** `SchemeHandler.isDocument` says by rule which `vault:` files WebKit would show as a document (HTML, anything with `xml` in its type, a web archive), and each gets `Content-Security-Policy: sandbox`; a list of types missed `application/rss+xml`, whose XHTML `<script>` ran and reached the app. The message handlers answer the main frame only (`Coordinator.hears`).
- **The page names only what the app gave it.** A message from the reader that names a task of another note (`toggleTask`, `editTask`) is taken only for a (path, line) a ` ```tasks ` query of this show answered with, and a `detected` number or address only when `Detected` found it in the note on screen (`PageTrust` in `ReaderView.swift`, made new at each show). The page is drawn from notes; the app never acts on a path or a number only because the page said it.
- **An edit reads the file again and refuses when the line changed.** `VaultEdits.toggleTask` checks that the clicked line is still a task with the status the view showed. Never write from what the view or the index remembers. Before it reads, the store has the editors save (`VaultStore.afterEditors`, `flushEditors`): a tick, a status, the task form, a board drop, Sort Tasks, a tag rename, a restore from the history, a sync and a pull all wait for it, so the edit reads what was typed and no editor writes its older text over the edit. Saving waits for Neovim, so with an editor open such an edit runs a moment later and its `Bool` answer is true; the failure is a notice. A new edit of a note outside an editor goes through the same gate.
- **The index is in memory and is built at launch.** The files are the record; there is no database on disk to migrate. File events are gathered for 250 ms and applied together. The files of `.obsidian` the store keeps a copy of (`FileWatcher.settings`: daily notes, templates, bookmarks, Iconic, `app.json`) are watched too and read again when they change, so a pull's bookmark or daily-notes folder needs no restart. When FSEvents says it lost events (`MustScanSubDirs`, `UserDropped`, `KernelDropped`) the paths it gives are not the files that changed: `VaultStore.rescan` reads the whole vault again, one run at a time.
- **The reader page reaches nothing but two schemes:** `daftar://reader/…` (the bundle) and `vault:///…` (the vault, and nothing outside it). The page has a content security policy; keep `script-src 'self'`, `base-uri 'none'` and `form-action 'none'`. The main frame loads `index.html` when the app asks for it (`Coordinator.loads`) and nothing else, not even another `daftar://reader/` file: a page with no `reader.js` in it would leave the pane dead.
- **A note's raw HTML goes through a list of what is allowed** (`web/src/sanitize.js`, no DOM, so node and Quick Look's JavaScriptCore run it): each tag is read and written again with its listed attributes, so nothing a note writes carries a `class`, an `id`, a `data-*` or an `on*` attribute, which are how the page knows its own controls. `script`, `style`, `iframe`, `svg`, `video` and their like go with what they hold; `meta`, `base`, `link`, `form`, `input` and the rest of HTML go, tag only; a `style` keeps only its listed properties with plain values (no `url(`); a name that is no element (`<first name>`) is shown as text. A new element or attribute for notes is a line in that file's lists and a case in `web/test/sanitize.test.mjs`; what the renderer itself writes (embeds, callouts, tasks) never goes through it.
- **The week notes in `Calendar/` are read-only here.** The phone writes them whole at every change; see `Calendar/CLAUDE.md` in the vault for the format.
- **Git runs with `GIT_TERMINAL_PROMPT=0` and `ssh -o BatchMode=yes`.** A sync that needs a password fails and says so; it never waits. Nor does it wait for a host that is gone: the `ssh` has `ConnectTimeout` and `ServerAliveInterval` (`Git.sshCommand(configured:environment:)`: the person's `GIT_SSH_COMMAND` as it is, else the clone's `core.sshCommand` with the app's options after it, else `ssh` with them; the config is read only for a command that reaches a remote, `Git.reachesRemote`), HTTPS has git's low-speed limit, and a command past `Git.limit` (300 seconds) is ended and fails with `timedOut`, so `VaultStore.syncing` cannot stay true for ever. Commit messages use the obsidian-git format of the vault's history: `update notes @ 2026-10-25 09:30:00 on host`. A sync commits nothing on a detached HEAD or a branch with no upstream (`refuseNoBranch`): it says what to do instead. A commit the repository's `pre-commit` or `commit-msg` hook refuses fails with `Git.Failure.hook`, and the notice names the hook and gives its last line.
- **A change of vault is one path, in the running app, and leaves nothing of the vault before.** `Vaults` (core, pure, over the text of `config.toml`) is the list: `vault` is the one in use, `vaults` every one known, a folder compared after `~`, `.` and `..` are resolved (links not followed), never twice, the one in use always among them, a new one written with `~` at the end; a file with `vault` and no `vaults` is that list and is not rewritten until the list changes. `vaults` is never read from a vault's `.daftar.toml` (`ResolvedSettings.top`). `VaultStore.change(to:)` is what Switch Vault, Open Vault…, Settings and an edit of the settings file all reach (`open` calls it once a vault is open): a folder that is not there is refused with a notice; the editors save, and an editor that still holds unsaved text (`unsaved`, each plain editor's `hasUnsaved`) stops the change; the notes typed in are formatted while their vault is still open; a sync that runs finishes, with a notice that the change waits; the tabs of the window the person is in (`WindowTabs.forChange`, that window first) are written to `tabs-<hash>.json` in the state folder (`VaultTabs`, the hash `places-<hash>.json` has) and the new vault's are opened again there by `WindowTabs.show`, as new `WindowModel`s, each note at its reading place, while every other window shows the home page in one tab. `vault` and `vaults` are written by `switchTo`, so only once the change is not refused, and a start writes nothing. `switchTo` calls `leave()` first, which empties what the vault before put in the store: the index and with it quick open, search, the tasks and `TaskStatuses.current`, the git state (`isRepository`, `gitStatus`, a rebase's conflicts, the last sync and its error), the read-only mark, the Problems panel (`VaultChecks.left`), the pending file events, the sync timers and the caches. What a new piece of state must do: be emptied in `leave()`, or be keyed by the vault's folder. A task that outlives the change checks the root it started with (`formatOnLeave`, the index's own load). No restart is used for any state. The spec is `docs/specs/several-vaults.md` in notes-linux, and `SeveralVaultsTests.aChangeLeavesNothingOfTheVaultBefore` is the test to add a line to.
- **The tabs are kept for a change of vault, not across launches.** A window's tabs are in memory (`WindowTabs`); nothing writes them at Quit and a start shows the home page, as before. `VaultTabs` writes them when a vault is left and reads them when it is opened again in the same or a later run.
- **A read-only vault is refused at the write, not at the button.** `daftar.readonly` in the clone's own git config (`git config --local --type=bool`, never the global one; a value that is no boolean reads as read-only) makes the vault read-only. Every write of the app passes `VaultEdits.refuseReadOnly` before it reads anything: `VaultEdits.apply`, `VaultMoves.perform` and `Bookmarks.save` in core, and in the store `write`, `afterEditors` (every edit of a note outside an editor), a new note or folder, a move, a delete, an icon, a pasted picture, Fix and Format Note. A new way to write gets that call first; a button that is off is only how it is shown. The answer is asked of git and kept by the stamp of the clone's config file (`ReadOnlyClones`), so a `git config` in a shell holds for the next write, and `VaultStore.readOnly` (the badge, the controls) follows at the next status, sync or when the app comes to the front. `Git.sync` and `Git.pull` are `pullOnly` in such a clone (`git pull --no-rebase --ff-only --no-autostash`): no commit, no push, no stash, and a clone with changes of its own fails with `SyncFailure.readOnlyDiverged` and its files. A push the remote refuses for a read-only key is `pushRefusedReadOnly` (`Git.refusedPush`), and the notice offers to make the vault read-only. What is not in the vault (reading places, the drill's state, the indexes, the settings) is still written. With `agents.read_only_clones = false` in the vault's `.daftar.toml`, `VaultStore.refusesAgents` keeps `NoteAssistant` from reading a note in a read-only clone. The spec is `docs/specs/read-only-vault.md` in notes-linux.
- **What one clone is lives in its git config, and Settings › Vault › Git writes only that** (`VaultSettingsView.swift`, `GitClone.swift`): `daftar.readonly`, `remote.<name>.url` (the remote of the branch's upstream, else `origin`; `git remote set-url`, or `git remote add` with the branch's upstream written as config, which the next pull fetches), `user.name`, `user.email` and `core.sshCommand`, each with `git config --local`, an emptied field unsetting its key. The key field writes `SSHKey.command(key:)` and reads it back with `SSHKey.key(in:)`; any other command is shown as text and its buttons are off. Generate is `ssh-keygen` into `~/.ssh/daftar_<vault>_ed25519`, never over a file. None of these is ever read from `.daftar.toml`.
- **The vault's `.daftar.toml` may set the app's settings, by a list.** `ResolvedSettings.resolved(vault:computer:root:)` (core, pure) gives each key the vault's value when the key is on `ResolvedSettings.allowed` and its value is of the key's kind and range, else the computer's, else the template's; `vault_settings` in `config.toml` declines all or some. `AppSettings.load` reads through it (`follow(vault:root:)`, called by the store when a vault opens, when the file changes and after each sync), so every property is the resolved value and `fromVault` names the keys whose controls show "From the vault" (`.fromVault(key, settings)`). A new setting gets its line in the shared spec's table and in `allowed` (or, when only the Mac has it, in `platformOnly` and in the README's table) in the same change, or the vault's value for it is refused and a change of it stays on the Mac: a key that names a program, sends something out or leaves the vault is never added. A notification rule's keys (`notifications.rules.<id>.note` and the others) cannot be listed by name, so `ResolvedSettings.shared` takes them by `NotificationRule.kinds`; `NotificationRule.all` reads the rules in `orderedKeys` order, the vault's first (`docs/specs/notification-rules.md`). `git.name` and `git.email` exist only in the vault's file: `Git.identity` passes them as `-c user.name=…` for a commit, a pull's rebase and `rebase --continue`, each only when the clone's own config has none. The spec is `docs/specs/vault-config.md` in notes-linux.
- **A note with a `type` is an OKF concept, and nothing is ever refused for it.** `OKF` (core) reads the front matter with the consumer rules of the Open Knowledge Format 0.3: null, an empty text and an empty list are an absent key, one mapping under `verified` is a list of one, an event without `by` and `at` is left out, a time is a date-time with an offset or a day (UTC), a malformed `stale_after` is stale, an unknown `status` is kept and is not stable, and the trust tier comes from the events at or after `generated.at`. `ParsedNote.concept` holds it (read only from a front matter with a `type:` line), and `VaultIndex.concept(of:)` is the question to ask, since `index.md` and `log.md` are never concepts. The YAML reader of the bases leaves `{ by: x, at: y }` as text: `OKF.mapping` reads it. Mark as Verified (`OKF.markVerified`, `VaultStore.markVerified`) writes only the lines of the `verified` key, as a block list of `{ by: …, at: … }` items, and every other line stays byte for byte; it is not `PropertySheet`'s write, which refuses a nested map. The actor is `okf.actor` of the settings, the computer's own and never read from a vault, else the name before the `@` of git's `user.email`. The inspector's Concept section, the reader's line (`ConceptLine`, SwiftUI above the page, not in the page) and the dimmed rows are `ConceptViews.swift`. The audit's `okf-*` findings are `daftar-cli check`'s and show in the Problems panel as any finding does. The spec is `docs/specs/open-knowledge-format.md` in notes-linux.
- **A Markdown link resolves as OKF says, then as a wikilink.** `Link.markdown` marks `[text](target)`, and `VaultIndex.resolve(_:from:)` (a `Link`) is what resolves a parsed link: `OKF.resolve` from the note's folder, or for a `/` path from the bundle root (`VaultIndex.bundleRoots`, the folders whose `index.md` has `okf_version`), which never climbs above its floor, so a target that leaves the vault is no file and is never read. A plain name that is no file there (`[x](Note.md)` for a note elsewhere) is still found as a wikilink is, as before OKF; a `/`, `./` or `../` path is only what it says. Never resolve a parsed link by its target's text alone. A move writes the link again in the form it had (`VaultMoves`): a `/` path from its bundle root, a relative one relative, percent-encoded.
- **A setting changed in the app goes to the vault's `.daftar.toml`.** `AppSettings.write`, which every property's `didSet` reaches (Settings, the zoom, the export panel alike), asks `ResolvedSettings.destination` where the change goes: the device (`config.toml`) for a key or a value a vault may never hold, a key the Mac declines, and a vault that cannot be written (`vaultWritable`, which the store keeps: not a read-only clone, and a repository or a folder that has the file); the platform's table (`[macos.…]`) for a key that is there already, a font, the terminal's font size and what only the Mac has (`platformOnly`); else the shared section. The vault's file is written by `VaultStore.writeVaultSetting`: the store's own gate (`refuseReadOnly`), the file read again, `ConfigFile.set` on the one line, an atomic write, `requestSync`; never by the settings object itself. The app then holds the text it wrote (`vaultText`), so the watcher's news of the same text changes nothing: no second read, no value going back. A property set to the value in use writes nothing, so a field that is only left (`HiddenNamesField`) makes no change in the repository. `resolved` reads the platform's table over the shared sections and never another platform's, with the same list, ranges and path rule. Keep on This Device and Follow the Vault (`keepOnDevice`, `followVault`, the context menu of `.fromVault`) add a key to `vault_settings` and take it off. A change to the device of a key the vault still sets holds until the settings are read again. The spec is section 5 of `docs/specs/vault-config.md`.
- **Colors are Daftar's:** naz on dark, Daylight on light, copied from `notes-droid/app/.../ui/theme/Naz.kt` and `Markup.kt`. They are in `web/src/reader.css`, in `Palette` (`WindowModel.swift`) and in the terminal's ANSI palette (`TerminalPane.swift`). Iconic's colour names map to naz as `IconColors.kt` does on the phone.
- **Iconic's icons are Lucide names; the tree draws SF Symbols.** `IconicImage.symbols` maps the ones the vault uses. A new icon in the vault needs a line there; an unknown or missing symbol draws the default icon.
- **The editor is TextKit 2 and never changes text to draw something.** Styling comes from `MarkdownHighlighter` (core, tested); an embedded image gets paragraph spacing and is drawn by `ImageLayoutFragment`, so the text, the cursor and undo see only `![[name.png]]`. An editor save goes through `VaultStore.write`; a change on disk is taken only when nothing is unsaved, as the one range that differs (`take`, never `string =`), and the undo stack goes with it: its steps name places in the old text. A file that does not read as UTF-8 (`VaultStore.isText`) gets no editor and is never written over: read as nothing, it would open empty and the first key would replace it.
- **The editor's code is by part.** `EditorView.swift` is the SwiftUI view and `EditorController`: loading, saving, following the disk, Neovim's start and end. `EditorStyling.swift` styles (an extension of the controller), `NoteTextView.swift` is the text view (carets, panels, margins), `NeovimView.swift` the view in Neovim mode (Neovim's edits, the scroll, the keys to Neovim), `EditorKeys.swift` the plain editor's keys, `EditorContainer.swift` the bar under the text; `EditorCursors.swift`, `EditorModes.swift`, `EditorImages.swift` and `EditorCompletion.swift` are as their names say. A stored property stays in its class's own file; what another file reads is not `private`.
- **The editor styles only what an edit can change.** A key restyles its own lines; the rest of the note is restyled, from the edited line on, only when the note's structure changed -- its fence, `$$`, `%%` and `---` lines, in order (`EditorController.structure`, kept with their places: a key finds the marks of its own lines and the lines beside them, `marks(after:)`) -- and the line after the edited ones starts in another block state than before the key (`BlockStates.known(at:)`); a fence whose language changed restyles its own block. An edit, or a selection's change of lines, of more than `atOnce` letters styles the screens at the cursor at once and the rest a part at a time (`restyleProgressively`), as a note does when it opens; many cursors style the lines of their edits (`editPieces`), not all between them. Attributes set outside `didProcessEditing` go in between `beginEditing` and `endEditing`: each attribute set alone is an edit of its own, and TextKit drops and finds again the layout after it. Text goes in with `setAttributedString` and plain attributes, never `string =`, which gives it the old text's attributes. A full restyle of a 70,000-character note is about 200 ms; a key must stay under a few. `just bench-editor` times the main thread from a key to its frame on a long note in a window; `EditorTests.eachKeyStylesTheNoteAsAWholeRestyleWould` checks incremental styling against a whole restyle.
- **The properties form writes only the lines it changed.** `PropertySheet` (core) keeps each property's lines as written and prints an untouched one byte for byte; a changed one keeps its quotes and its list style. YAML it cannot print back the same (comments, anchors, nested maps, block scalars, a key twice) is never a form: the editor shows it raw. The editor hides the front matter the form shows with attributes (`collapseFrontMatter`) and keeps the cursor and typing out of it (`PropertiesView.swift`); a form edit is `VaultStore.editProperties`, which saves the editors, reads the file again and refuses when the front matter is not the one the form showed. `PropertySheet` has a `RobustnessTests` line.
- **Live preview hides marks with attributes, never by changing text.** Away from the lines the selection is on, `.markup` spans, a markdown link's brackets and address, and a highlight's colour emoji get a 0.01 pt clear font; a quote's `>` stays, and a callout's `>` and `[!type]` go. A selection change restyles the old and the new lines only (`revealSelection`). The cursor never sits in hidden text, so the arrows never stop on it.
- **A drawn part is a way to see the text, never the text** (`docs/specs/look.md` in notes-linux, part 2). Before this, the next sync committed the conflict marks on a detached HEAD and every later pull failed. In a rebase git's "ours" is the upstream and "theirs" is the person's commit: say "On the remote" and "Your change", never ours and theirs. `rebase --continue` runs with `GIT_EDITOR=true`, in a loop, since the next replayed commit can stop too, and after `git add -A`: it refuses a tree with changes that are not staged, and the person may tick a task or capture a line while the conflict waits, which then goes into the replayed commit. Format Note in the plain editor replaces the one range that differs as one undo group; in Neovim mode it sets the changed lines with `nvim_buf_set_lines` (one step of Neovim's undo) and writes. No `daftar-cli`, or one too old, formats nothing and says nothing, except on the command.
- **Search by meaning is `daftar-cli`'s** (`MeaningSearch.swift`; `Meaning` in core reads its JSON and its failures; the spec is `docs/specs/meaning-search.md` in notes-linux): `search --meaning-only --json`, `related --json` and `semantic-index`, run by `DaftarCLI` in the vault's folder. A search waits for a pause in the typing and cancels the run before it. Exit 3 is a model not downloaded, and the one row offers the download; a usage error about these flags is an old `daftar-cli`, said once and not asked again until the binary changes. The model is never downloaded unasked, and the background refresh (`meaning.refresh_minutes` after the last change, `.background` priority, one build at a time) runs only once the model is there.
- **The dark palette is screen-only** (`@media screen and (prefers-color-scheme: dark)` in `reader.css`), so a PDF export or a print is always in Daylight.
- **A fold is how a note is shown, and a note opens folded when the vault or the app says so.** `reader.folded` in the vault's `.daftar.toml` (`VaultSettings`, core; read at open and when the file changes, `FileWatcher.vault`) and `appearance.fold_sections` (`vault`, `always`, `never`) give `VaultStore.foldsSections`. The page gets `folds` (the list kept for the note, or `null`) and `folded`: with no list kept and `folded`, it shuts every heading that holds something (`folds.shutAll`). `ReadingPlaces.keptFolds` tells no list from an empty one, and an empty one is kept only where notes open folded (`setFolds(explicit:)`), so a note opened whole stays open. A folded heading says what it holds (`foldHint` in `controls.js`, tested in node; `folds.hint` counts, once for each heading of a page): the hint is a `.fold-hint` span in the heading, so whatever reads a heading's text leaves it out (the copied link, read aloud), and it is not printed. Passing an optional to the page: `value.map { $0 as Any } ?? NSNull()`, never `value as Any?`, which wraps the empty optional and is not `null` there. The spec is `docs/specs/folded-sections.md` in notes-linux; `FoldedNotesTests` has the page's cases in a real web view.
- **The reading cursor is a block with a band on one line of it.** `reading` in `web/src/reader.js`: a block is the innermost element with a `data-line`; its lines are the rects of its text nodes (not a nested list, a picture or KaTeX's hidden text) merged where they share most of their height (`rows`). `j`/`k` go a line at a time and on to the next block after its last line; a block of one line has no band. The file line of a line (`sourceLine`) is the block's line plus the `\n` in its text before the line's start, found with `caretRangeFromPoint` (soft breaks stay `\n` since markdown-it runs with `breaks: false`; a fence adds one); off screen it is unknown, never guessed. `appearance.reading_line` is the band's strength, 0 none. After a scroll, a cursor left off screen comes to the first line on screen (`follow`), so `NotePane.cursorLine` is always where the person reads: ⌘E opens the editor there and the reader comes back to the editor's line. That hand-off is the pane's, both ways; test it end to end.
- **What stays at the top of the reader is measured once a frame, reads before writes.** The section bar (`sectionBar`), a table's header that stays (`tableHead`, a copy in a layer of its own, since a table scrolls sideways in its own box and its header cannot stick to the window) and the progress line are set in `onScroll` in `web/src/reader.js`: `reportSection` and the `measure` functions read boxes, then the `apply` functions write. The headings and the tables are listed once a drawing (`sections.list`, `sections.tables`; `forgetPage` clears them). A page that draws no frame has no `requestAnimationFrame`: `onScroll` and `softly` each have a timer beside it, and the tests' window, which is off screen, goes that way. The rules that need no page are apart, tested in node: `sectionbar.js` (the heading path, the parents left out), `tablesort.js` (a sort is the rows on the page moved, never the file; it is kept by the table's place and header texts through a redraw of the same note) and the markup in `controls.js`. The spec is "Reader" in `docs/specs/look.md` in notes-linux, and `ReaderPartTwoTests` has the page's cases in a real web view. A table's row is a line of the file (the header, the dashes, then each row), and a sorted row keeps the line it has in the file (`fileOrder`): `reading.sourceLine` and `reading.restore` go by it, so the reading cursor stays on its row through a sort and a redraw, and the editor opens at that row. The section bar's path is measured with the last heading at its whole width (`is-measured`): on the line it gives way first, and two parents that fit by themselves would squeeze it out.
- **A link's card gets the note's first lines from the app, never the whole note.** The page asks with the `preview` message (`ReaderView.Coordinator.preview`), and `LinkPreview.excerpt` (core, the same rule in every app) cuts the text: 12 lines or 600 characters, the section or the block the link names, a cut code block closed, an embed written as its link. The card (`preview` in `reader.js`) is also the footnote's popover; it never takes the focus, nothing in it is a Tab stop, and the links of a note's card are not live.
- **The soft change is the page's between two notes and the pane's between reading and editing** (`SoftChange.swift`). The page draws the new note inside a view transition (`softly`), so the new note is at its place before the fade starts. Into the editor, the editor fades in over the page, which stays seen until the fade is over (`coveredReader`). Back to reading, the editor leaves at once, as before, so its save and its Neovim are not held for the fade, and a picture of it fades out over the page that has drawn (`SoftChange.leave`, removed by the clock, never by the animation's end). The keys are the coming view's from the start. Until the page has drawn the new note it takes no click and no plain key (`leaving` in `reader.js`): the app already has the new note, a task's box names its line with no path, and a click on the note that leaves ticked that line of the new one. That gate is only the page's, and the page hears of the new note late (it may be busy): so every message the page posts carries `note`, the path of the note it has drawn (`onPage`), and the app drops a message whose `note` is not the note it shows (`ReaderView.Coordinator`, `aClickThePageMadeBeforeItHeardOfTheNextNoteTicksNothing`). This is by state, never by a delay. A test's window is not seen, and a page that is not seen makes no soft change, and neither does one with Reduce Motion, which a CI runner may have on: a test of the soft change says first that the page is seen and that motion is wanted (`aClickOnTheNoteThatLeavesTicksNothing`); a page that is not seen runs no CSS transition either, so read a style, not a box, of what moves.
- **The reader stays loaded under the editor.** `NotePane`'s content is a `ZStack`: the editor over a hidden `ReaderView` with `active: false`, which draws nothing new and takes no keys (`Coordinator.paused`), and whose `onCursor` and `onSection` are ignored while the pane edits. Back to reading, the page saves the editors first (`flushEditors`, so it draws what Neovim just wrote), draws at the editor's line and calls `onShown`; until then the editor stays over it (`NotePane.readerShown`, with a 0.5 s fallback), so the page is never seen blank or at its old place. Into the editor, `go(toLine:)` centres the view on the line before Neovim runs, and `NeovimSession.start` puts Neovim's cursor there before its cursor reports begin, so the cursor never slides from line 1. A Neovim cursor whose place in the text did not change (`neovimCursorAt`) moves at once: a relayout or a scroll is not a move.
- **New Task (⌥⌘T, File menu and palette) is the task form with a note and a section.** `WindowModel.newTask` fills in the note on screen and the heading the cursor is under (the scratchpad with no note); `TaskLine.written` makes the line, with today as its ➕ created date, and `VaultStore.addTask` puts it at the end of that heading's section with `QuickCapture.append(_:to:headingLine:)`, through the editors' gate, reading the file again. The heading is found by its line, not its name, so two `## Work` sections are two places. The form's Created row edits ➕ on any task.
- **Drill is `daftar-core`'s `drill.rs`, ported, and shares its state file.** `Drill` (core) makes the same cards, ids (`path#Heading#Under it`) and SM-2 schedule, and `DrillState` reads and writes `$XDG_STATE_HOME/daftar/drill-<FNV-1a of the vault's path>.json` (else `~/.local/state`) byte for byte as serde_json does (`DrillTests` has a file the CLI wrote), never `stateDirectory`: the app, `daftar-cli drill` and the MCP `drill_*` tools share one history. A test's `AppSettings` keep it in their own state folder (`AppSettings.drillFolder`). A rating reads the file again and writes through a temporary file and a rename, so a rating made elsewhere is kept. `DrillDeck` (on the store) reads the deck off the main thread; the answer is the reader given the section's text (`ReaderRequest.text`), which ticks no task, keeps no folds and takes no keys, since its lines are not the file's; it lays out hidden (`isHidden`, so VoiceOver does not read it early) and only paints on the flip. The page's keys are a local monitor by key code, so they work in any keyboard layout.
- **An error in `daftar.show` leaves the page at its top, silently.** The note is drawn, then the scroll, folds and reading cursor are skipped. A reference to a name that is not there (`scrollToLine` once used an `anchor` it was never given) did this for every return from the editor. The node tests do not load `reader.js`; a change to it gets a test in a real `WKWebView` (`ReadingCursorTests`, `ImagePageTests`), which also catches a page that never gets ready.
- **A `@MainActor` suite's `.enabled(if:)` deadlocks the whole test run before it starts.** Put the condition in a global constant.
- **A window has one or two note panes (`NotePane`).** Each pane has its own note, mode, history and find; `WindowModel` keeps the panes and the focused one, and its `request`, `editing`, `path` and history commands act on the focused pane, so menus, quick open and the inspector follow the focus. A click in a pane gives it the focus (`PaneClicks`, a local mouse monitor) before the click acts. The editor saves when it stops being first responder and takes the file when it becomes first responder again with nothing unsaved, so the same note in the editor of two panes does not lose text. In Neovim mode only one pane edits (`WindowModel.oneEditor`): two Neovims would each own the same file. The split is not kept across launches; no window state is.
- **The Dock badge, the alerts and Spotlight follow the vault for the app, not for a window.** `VaultFollower` (`DaftarApp.swift`) hears the store's changes with `withObservationTracking`, started from the menu bar icon's label as quick capture is, so each change is followed once however many windows are open, and with none open. Never hang such work on a window's view. `Spotlight` stops after the index refuses a batch (an ad-hoc build always does), until the next launch.
- **Quick capture works with no window open.** The store belongs to the app; `QuickCaptureController` gets it from the menu bar icon's label, which is there from launch. The shortcut is a Carbon hot key (`RegisterEventHotKey`, no Accessibility permission) and the panel is a non-activating `NSPanel`, so the app in front stays in front. A capture saves the editors, reads the file again and writes with `VaultStore.write`; `QuickCapture.append` (core) keeps every line. `capture.heading` is filled as a template is (`VaultStore.captureHeading`), so `## {{date:YYYY-MM-DD}}` gives one inbox note a section for each day.
- **Services (Add to Daftar Scratchpad, New Daftar Task) work with no window.** `NSServices` in `Support/Info.plist` and `DaftarServices` (`Services.swift`), the app's `servicesProvider` from launch, with the store quick capture has, waited for while it loads. The scratchpad line is written by `VaultStore.addToScratchpad` (the editors' gate, the file read again, `QuickCapture.append` under `## <today>`), and a failure opens quick capture with the line, so nothing sent is lost. New Daftar Task sends `daftar://new-task?text=` to this process as an Apple event (`openInThisApp`), so SwiftUI makes a window when none is open and the installed app never gets a test build's address; the address only fills the form. To try a service from a test build, give a copy its own bundle ID, name and `NSPortName`, start it with `open -n` and a test `XDG_CONFIG_HOME` first (a service that has to launch the app gives it no environment, so it would read the real config), then `lsregister -f` it and `/System/Library/CoreServices/pbs -update`.
- **The scratchpad is one note.** ⌥⌘S (File › Scratchpad, the palette) opens `scratchpad.note`, a vault path, `Scratchpad.md` when not set: made empty when it is not there, opened in the editor with the cursor at its end, and nothing is written into it by opening it. It never makes a note for each day or a folder; the older `scratchpad.folder` key is not read and not rewritten. The vault keeps one inbox with dated sections, as Daftar for Android's `scratchpadPath` does; quick capture reaches the same note with `capture.target` and a dated `capture.heading`. Daftar for Linux has to follow.
- **Every control has a name VoiceOver can say.** An icon-only button gets `.accessibilityLabel` (and `.help`); a decorative image is `.accessibilityHidden(true)`; a row drawn with `onTapGesture` gets `accessibilityRow` (`Accessibility.swift`); what a colour or an icon alone says (status, priority, overdue, a dot, the focused pane) is said in words, from `Spoken` (core) for tasks. In the reader every control is a real `<button>` or has a `role` and a name (`web/src/controls.js`, tested in `web/test/a11y.test.mjs`). Animations go through `withMotion` or `motionAnimation`, and faint text through `.faint()`, so Reduce Motion and Increase Contrast hold. `AccessibilityTests` reads the views' tree with `NSAccessibility`; SwiftUI builds that tree only after the app gets `AXEnhancedUserInterface`, which the test sets.
- **The home page decodes its picture once.** A pane with no note shows `HomeView`; `HomePictures` decodes `home.image` off the main thread with ImageIO (no larger than 5120 px, as EXIF turns it) and keeps it by path and modification date, so a redraw never decodes. The page reads Beautitab's `data.json` (`Beautitab`, core, lenient) again each time it appears, never goes to the network (a web address or an online quote source is off), and the picture is `.accessibilityHidden`. ImageIO reads WebP but cannot write it: a test's WebP is a byte literal.
- **Hidden files leave the lists, never the index.** `ExcludedFiles` is Obsidian's `userIgnoreFilters` and the `files.hidden` names (whole file names, in any folder); `VaultStore.excluded` is what the lists leave out now (nothing while `files.show_hidden` is on), `VaultStore.hidden` the rule itself, which Spotlight follows. A list a person browses (the tree through `store.tree` and `store.folder`, quick open, search, the graph, backlinks, recent notes, Today, the board) filters with `store.excluded`; the resolver, the reader and `daftar://open` never do, so a link or an embed to a hidden file still works.
- **A block id is read the same in the app and the reader.** `BlockRefs` (core) and `blockIds` in `web/src/render.js`: a trailing ` ^id` names its paragraph or list item (the `<li>`, since a tight list draws no `<p>`), and a `^id` line of its own, after an empty line, names the table, quote or code block above it. A new id is six lowercase letters and digits, free in the note, and goes in through the editor (a step to undo) or `VaultStore.addBlockId`, which reads the file again and refuses a block that changed. The editor's completion list shows labels (`alias → Note`, an indented heading, `#tag  3`); `CompletionState.choices` maps each label to the text it writes, so a label never goes into the note.
- **The job search is `job_search.rs` ported.** `JobSearch` (core) reads applications from the index's front matter (`job_stage` and the other `job_` keys), its stages, channels, `upcoming` and `forMeeting` follow the Rust tests, and `QuietRules` is `memory.rs`'s `memory-quiet` (`.daftar.toml`'s `active` and `quiet_days`). `job_next` is a wall-clock time in Europe/Madrid (`LocalTime.zone`), whatever the Mac's zone. The board (`JobBoardView`) reads it off the main thread at each index revision; a drop is `VaultStore.setJobStage`, through the editors' gate, which writes the one `job_stage` line with `PropertySheet` and refuses when the note's stage is not the card's. It writes nothing else: not `Tasks/Interviews.md`, not the history.
- **Holidays are code, not vault data.** `CalendarEvents` (core) is the table of `calendar_events.rs` in notes-linux and `docs/specs/calendar-events.md`; a change to a day changes all three apps. An event's note is the vault's note named by its title (`VaultStore.note(of:)`), never made by the app. `DayPicker` draws a `Month` (core): Gregorian from Monday, or with `appearance.persian_calendar` the Jalali month from Saturday, read from the right; a day picked is always written as its Gregorian `YYYY-MM-DD`.
- **`appearance.remote_images = false` asks no site for a picture, by two rules.** The renderer: every picture a note or a base draws is written by `picture` in `web/src/render.js` (`![…](…)`, a raw `<img>`, a base card's cover), which reads the address as the browser does (`pictureAddress`: `https:/x`, `https:x`, a tab or a character reference in the scheme are all `https://x`; an `http:` picture is asked for over https) and writes a `remote-image` placeholder; there is no HTML to search afterwards. The page's policy: `SchemeHandler` serves `index.html` with `img-src` without `https:` while the setting is off (`noRemotePictures`), so what the renderer misses (Mermaid asks for a picture shape itself) is refused before any site is asked; a change of the setting loads the page again. A click on a placeholder asks the app (`remoteImage` handler), which allows that one `https:` address for the note on screen and answers with a `daftar-remote:` address that `RemotePictures` serves; an address nobody clicked is refused there. The host only sends `remoteImages` with `daftar.show` (`ReaderView.appearance`). The spec is `docs/specs/remote-images.md` in notes-linux.
- **The terminal is SwiftTerm, pinned exactly.** It runs the login shell in the vault's folder and lives in the window's model, so hiding the pane keeps the shell.

## Performance

`just bench` (`BenchmarkTests`, on only with `DAFTAR_BENCH=1`) writes a vault from a fixed seed: 20,000 notes in nested folders, 53,000 tasks, front matter, links (broken, with an alias, with a heading), ` ```tasks ` queries, 70,000-character notes, Persian text, images and bases. It prints a table of the paths a person waits on. The budget on an M4 Pro, with the release build:

| Path | Budget |
|---|---|
| Open the vault (index and full-text search) | under 2.5 s |
| A saved note (watcher batch of 1) | under 150 ms |
| A pull of 500 changed files | under 300 ms |
| Full-text search | under 50 ms |
| Quick open, each key | under 100 ms |
| A ` ```tasks ` query over every task, or the Today page | under 100 ms |
| The whole-vault graph and its layout | under 1.5 s |
| Rename a note that 2,000 notes link to | under 1.5 s |
| Rename a tag in 6,000 notes | under 2 s |

A change that makes a row slower than its budget is a bug. To find a slow path, run it in a loop and `sample <pid>` the test process (Instruments needs Xcode). Rules the timings taught:

- **A regular expression runs only on a line that has its marks.** Swift's `Regex` is slow: test for the ASCII marks it needs first (`hasMark("[[")`, `mayHoldTag`), on the UTF-8 bytes, not with Foundation's `contains`. The test must be a condition the pattern cannot match without, so the result never changes.
- **No regex literal and no `Calendar(identifier:)` inside a function that runs per line or per task;** make it a `static let`.
- **A sort compares values worked out before it**, not in its comparator: titles, query groups, and positions rather than large structs.
- **`derive()` makes the resolver and the tree again only when the files changed.** A saved note changes neither.
- **The full-text search fills after the index.** `Vault.index` hands the notes to `SearchIndex.fillLater` and returns, so the vault opens without waiting for FTS5 (430 ms of 1.3 s on 2,800 notes); a search, put or remove waits for the fill (`filling`), so none answers from part of the vault.
- **The search table deletes by rowid.** Its `path` column is not indexed; a delete by path reads the whole table.
- **Work on many independent files or nodes is shared out with `concurrentPerform`**, each in its own slot of an `UnsafeMutableBufferPointer`, with the same order of operations, so the result is the same to the last bit. Deinitialize the buffer before it is deallocated, or what it holds leaks.

### A window and its tabs

The tabs are Daftar's own (`WindowTabs`), not AppKit's window tabs. As window tabs each tab was an `NSWindow` with a sidebar, a toolbar and a SwiftUI root of its own, so a new tab made and laid out a whole window and a switch showed another one. Now a window has one sidebar, one toolbar and one inspector, and a tab is a `WindowModel` whose note panes stay in the window, unseen, while another tab is in front. Measured on a copy of the real vault on an M4 Pro, in full screen, in view, with eight tabs, as the time the main thread does not answer:

| Path | 0.22.1 | 0.22.3 | 0.23.0 | Budget |
|---|---|---|---|---|
| New Tab | 870 ms, and 65 ms more for each tab open | 365 ms | 72 ms, the tab on screen after 50 | under 100 ms |
| Switch to another tab | 590 ms | 115 ms | 85 ms, the note on screen after 10 to 40 | under 100 ms, the note under 50 |
| Open a note | 650 to 990 ms | 85 to 160 ms | 80 to 110 ms | under 120 ms |
| A file changes | 600 to 770 ms | 35 to 140 ms | 36 to 55 ms | under 60 ms |

Memory with eight tabs, seven of them on notes: 384 MB (a dozen window tabs were 670 MB to 1 GB).

The rules:

- **`WindowTabs` has the tabs and two tabs in front.** `current` is the tab whose note the window shows; `chrome` is the tab the sidebar, the toolbar, the inspector, the title and the sheets show, which is `current` a turn of the run loop later. So the note of a tab is on screen first (about 25 ms of work) and what stands around it (about 60 ms: the inspector's rows, the sidebar's selection, the title) in the next frame. `ContentView` reads `tabs.chrome`; `TabDetails` and `TabStrip` read `tabs.current`.
- **A tab left stays in the window.** `TabDetails` is a `ZStack` of every tab's `WindowDetail`, the ones behind with no opacity, no hit testing and hidden from VoiceOver. Its reader is paused (`ReaderView.shown`, as `active` pauses a page under the editor), so a tab behind draws nothing when a file changes, and comes back as it was left. Never make a tab's views again to show it: a page loaded again is 100 ms and loses its place.
- **The keys follow the tab.** `WindowTabs.select` takes the keys from the tab left (its views are still in the window and would keep the first responder), remembers who had them, and gives them back when the tab is shown again. A page takes them when it comes back or has drawn a new note and nothing has them (`takeKeys(ifFree:)`); the home page's field takes them when its page is shown (`HomeView.takeKeys`). A tab is not a window: AppKit gives a new window's first view the keys, and nothing gives them to a new tab. `PerfScript`'s `key` and `state` lines test this in the app.
- **⌘W, ⌃Tab and the red button.** SwiftUI gives no say over Close, so `TabClose` changes `NSWindow.performClose(_:)`: it closes the tab in front while there is more than one, and the window from the red button (a sender that is an `NSButton`) or with one tab. ⌃Tab and ⌃⇧Tab are taken by a local monitor (`TabKeys`), since to AppKit ⌃Tab moves the keys to the next view; the Window menu names them and ⇧⌘] and ⇧⌘[ do the same. AppKit's window tabs are off (`NSWindow.allowsAutomaticWindowTabbing = false`, `tabbingMode = .disallowed`), or a second window would be a tab of the first beside Daftar's own; `tabbingIdentifier` is still `daftar.main`, which is how a Daftar window is known.
- **The bar of tabs is AppKit's in what it does and how it looks** (`TabStrip`): there with two tabs or more, above the notes and the inspector (a `VStack`, not a safe area inset: the inspector's column does not hear one, and the breadcrumb went under the bar), the tab in front in the control's own colour on a bar of the toolbar's material, a cross on the tab under the pointer (⌥ closes the others), the middle button closes, + opens. A tab is dragged as `daftar-tab:<tabID>` to another place or another window's bar (`WindowTabs.take`); Move Tab to New Window hands the tab to the window that opens (`handoff`, `takeHandoff`), and Merge All Windows brings every window's tabs to one. A tab that changes window keeps its `WindowModel`; its views are made again there. A window always has a tab: the last one to leave closes its window.
- **The toolbar has one shape.** `WindowToolbar` is made with the tabs' object, and each item is a view that reads `tabs.chrome` itself (`HistoryButton`, `HomeButton`, `ModePicker`, `ShareButton`, `TerminalToggle`, `InspectorButton`). A control with nothing to act on is dimmed, never left out: when Read or Edit and Share were there only with a note, a switch between the home page and a note took every toolbar item out and made it again, 140 ms of `NSToolbarView` layout. The toolbar itself reads only what changes rarely (a repository, a rebase, `VaultChecks.any`, never `counts`).
- **The inspector is a scrolling stack, and finds a note's facts once.** `InspectorList` is a `ScrollView` with a `LazyVStack`, not a `List`: a list's row is an AppKit row with a hosting view of its own, and each note shown took the last note's rows out and made the new one's. What it finds off the main thread (where the links go, the addresses, the unlinked mentions: `InspectorView.Facts`) is kept by note and vault revision in `InspectorCache`, with each note's related-notes query, so a note gone back to is drawn once, with everything. Never resolve links or search in `body`.
- **`DaftarApp.body` reads nothing that changes.** The menus are `AppCommands`, which reads the focused window and the store itself. Read in the app's `body`, the focused window, `window?.editing`, `store.isRepository` or a periodic note's neighbour made SwiftUI work out the scenes again and give every open window its root view again (`AppGraph.graphDidChange`, `updateRootHost`).
- **`ContentView.body` reads only `store.root`, `settled` and `tabs.chrome`.** The title and the `onChange` handlers are `WindowFollowing`, the tabs' notes are `TabDetails`, the banner is `NoticeBanner` and the toolbar is `WindowToolbar`. A new window fills its sidebar and toolbar after it is on screen (`settled`), not at each of AppKit's layouts of a new window.
- **The sidebar's search field is its own `NSSearchField`** (`SidebarSearchField`), never `.searchable(placement: .sidebar)`. That field is a toolbar item to SwiftUI, and with it SwiftUI took every toolbar item out and made it again (`AppKitToolbarItem` and its hosting view) each time the window became or stopped being the one in front. Search in Vault still finds the `NSSearchField` in the window (`SearchField.focus`).
- **Only a window in view follows the pointer for the sidebar's reveal at the screen's edge** (`EdgeHover`). In full screen AppKit's `NSSplitViewController` follows every move of the pointer, in any app, for each window, and asks the window server whether the window is on a Space in view. `EdgeHover` sets `revealsOnEdgeHoverInFullscreen` (not in AppKit's headers, so asked for with `responds(to:)`) off on a window that is not seen and on again when it is.

To measure such a path: a copy of the vault without `.git`, a test `XDG_CONFIG_HOME`, and `open -n -W --env DAFTAR_PERF=/path/script build/Daftar.app --args -ApplePersistenceIgnoreState YES` (a test build has the installed app's bundle ID and would open its saved tabs). `PerfScript` runs the script's lines in the app (`full`, `menu File>New Tab`, `open Note.md`, `tab 2`, `touch Note.md`, `key j`, `key cmd+w`, `state after ⌘W`, `shot /tmp/window.png`, `page after a change`, `append Note.md words`, `type 12 o- [ ] words\e`, `wait 3`, `quit`) and writes to `/path/script.log`, for each line, how long the main thread did not answer in the next two and a half seconds (`ms`), how long until it first answered again (`first`: when the window could draw), whether the window was seen and in full screen, and the time in AppKit's layout methods. A `type` line types its letters at that many a second, as a person does (`\n` is Return, `\e` Escape, `30r` a key held down), and logs each key's time until the editor's text or cursor changed, counted for the last key sent before the change (the first `y` of `yy` is silent, not slow), and the main thread's own time a key (`CLOCK_THREAD_CPUTIME_ID`); the scroll and the cursor at each change go to `/path/script.scroll`. Compare that CPU time between builds, not "key to view" between modes: the plain editor changes the text inside the key's event, and Neovim mode a moment later, before the same styling and drawing. A `state` line says the tabs, the one in front, each one's reading line and who has the keys, which is how the tabs' keys are tested without a keyboard; a `page` line says how much text the page in front shows and how it ends, which is how a change behind a tab is tested. `shot` is the window as the window server draws it, glass and all (`CGWindowListCreateImage`, found by name, which an app may call on its own window with no permission), so the look can be judged without Screen Recording. It needs no permission: an accessibility client that presses the menus measures the same, but a shell in tmux has no Accessibility permission, and `screencapture -l` no Screen Recording. To size a part of the window, leave it out behind an environment variable for one run (the inspector was 40 ms of a switch of tabs, the sidebar 18, the toolbar 13, the title 10, and the tab's own note 25): the sampler's shares are wrong for deep SwiftUI stacks, and this is not. `sample <pid>` slows the app several times over: use it for where the time goes, never for how long. A full screen window on a Space that is not in view draws nothing and answers in a third of the time: the log says `seen` or `hidden` at each line, and with the screen locked every variant measures the same, so compare two builds one after the other in the same state, or a build looks faster or slower than it is.

## Testing the app

The installed app comes from Homebrew only (`brew install --cask parham-alvani/tap/daftar`): a release (`VERSION` and a `v*` tag) reaches the tap's cask, and the cask installs it. A release is `VERSION` bumped in its own commit and a `v*` tag; CI takes about twenty minutes, then the tap's `bump` workflow (`gh workflow run bump.yaml` in `homebrew-tap`) moves the cask, and `brew upgrade --cask parham-alvani/tap/daftar` installs it. A running Daftar keeps its old code until it is quit and opened again: check its start time against the release before calling a fix missing. Never copy a test build into `/Applications`; that makes the cask install fail and hides which version is installed. Test from `build/Daftar.app` (`just app`), with `open -n` and a test `XDG_CONFIG_HOME`; a build run from `build/` asks for notification permission again. The vault is the `vault` line of the config file. `open "daftar://open?path=Folder/Note.md"` opens a note, `daftar://open?path=today` the Today page, and `daftar://terminal` the terminal. A debug build makes the web view inspectable in Safari.

A Carbon hot key fires for a synthetic key only when the modifier keys go down first, as on a keyboard (`CGEvent` at `.cghidEventTap`); a key posted to the app's pid never reaches it.

**Do not click a task in the real vault to test.** A tick writes the file, and with automatic sync on, it commits and pushes. Test writes on a copy, or with the unit tests.
